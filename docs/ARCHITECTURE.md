# Архитектура games.secrii.dev

Сайт с несколькими браузерными 2D/3D-играми. Игры пишутся одним автором (3–10 штук), платформа — десктоп.

## Принятые решения

| Вопрос          | Решение                                                             |
| --------------- | ------------------------------------------------------------------- |
| Мультиплеер     | Соревновательный realtime, авторитарный сервер (Colyseus)           |
| Аккаунты        | Гость по умолчанию + опциональный аккаунт                           |
| Встраивание игр | Прямо в страницу (`mount/unmount`), без iframe                      |
| Платформы       | Десктоп: клавиатура, мышь, геймпад. Тач и PWA не нужны              |
| Первая игра     | Оригинальная 3D-гонка по стройке мостов (рабочее название `bridge`) |

## Стек

| Слой              | Технология                                                           |
| ----------------- | -------------------------------------------------------------------- |
| Рантайм, монорепо | Bun workspaces                                                       |
| Линтер, форматтер | `bun lint`, `bun fmt` (встроены в Bun с 1.4.4), без ESLint/Prettier  |
| Оболочка сайта    | Next.js (App Router) + React 19 на рантайме Bun (`bun --bun`)        |
| 2D                | Phaser 4 (или PixiJS 8, если нужен только рендер)                    |
| 3D                | Three.js (WebGPURenderer с откатом на WebGL2), без R3F               |
| Физика            | Rapier (WASM), одна и та же в браузере и на сервере                  |
| Realtime          | Colyseus 0.18 + `@colyseus/bun-websockets`                           |
| API               | `Bun.serve` routes, zod-схемы в `packages/contracts`                 |
| БД                | Postgres через `Bun.sql` + Drizzle                                   |
| Кэш, presence     | Redis (`Bun.redis`), Colyseus RedisPresence                          |
| Авторизация       | Better Auth: анонимные сессии + аккаунты                             |
| Деплой            | Docker Compose на VPS: Caddy, web, api, game-server, Postgres, Redis |

### API: чистый Bun, а не Elysia 2 RC

Решение от 2026-11-18: `apps/api` пишем на `Bun.serve` без фреймворка.

- API тонкий: авторизация, профили, очки, лидерборды — порядка десятка эндпоинтов. Игровой трафик идёт через Colyseus, а не через API, так что производительность и богатый middleware здесь не нужны.
- RC в фундаменте — лишний риск: API может поменяться до релиза, документация и экосистема плагинов отстают.
- Всё нужное есть в Bun: `routes` с параметрами, `Request`/`Response`. Better Auth монтируется одной строкой (`"/api/auth/*": req => auth.handler(req)`).
- Типобезопасность клиент ↔ сервер даёт `packages/contracts`: zod-схемы запросов и ответов общие для `web` и `api`. Это заменяет Eden Treaty из Elysia.
- Что пишем сами (маленький модуль в `apps/api/src/http/`): валидация тела и query через zod-схему из `contracts`, единый формат ошибок, CORS, логирование запросов.

**Когда пересмотреть:** если понадобятся OpenAPI-документация, много middleware или эндпоинтов станет больше 30–40. К тому времени Elysia 2 выйдет из RC. Миграция дешёвая: обработчики тонкие, а zod-схемы из `contracts` Elysia принимает через Standard Schema.

### Web: Next.js, а не Bun SPA

Решение от 2026-11-19: `apps/web` пишем на Next.js (App Router). Остальные приложения и пакеты остаются на Bun.

Почему:

- **SEO, в том числе Яндекс.** Каталог и страницы игр должны отдавать текст в HTML. Google выполняет JS с задержкой, Яндекс — хуже Google, а SPA отдаёт пустой `<div id="root">`.
- **Превью ссылок-приглашений** (`/play/bridge?room=K7X2QP`) в мессенджерах, которые не выполняют JS. Нужны meta-теги для каждой страницы с сервера.
- **Первая загрузка страниц контента.** С SSG карточки каталога приходят готовым HTML, LCP не ждёт загрузки React.
- **Готовые оптимизации:** `next/image` для превью игр, `next/font`, prefetch ссылок, `generateMetadata`, `sitemap.ts`, ISR для лидербордов (M5).

Чего Next **не** даёт: производительность самой игры. Её определяют чанк игры, ассеты и наш цикл, поэтому страница игры — клиентский остров.

#### Как рендерится `web`

| Страница                 | Рендер                           | Что внутри                                                                                         |
| ------------------------ | -------------------------------- | -------------------------------------------------------------------------------------------------- |
| `/[locale]` (каталог)    | SSG                              | карточки из манифестов, `next/image`                                                               |
| `/[locale]/play/[id]`    | SSG-оболочка + клиентский остров | заголовок, описание, `generateMetadata` из манифеста; внутри клиентский `<GameHost>` с `mountGame` |
| лидерборды, профили (M5) | ISR / SSR                        | данные из `apps/api`                                                                               |

Правила:

- **Игра никогда не рендерится на сервере.** Модуль игры грузится только в браузере через `import()` из `gameLoader` и предзагружается при наведении на «Играть».
- **Каталог игр — серверный, загрузчик — клиентский.** `games` (`apps/web/src/games`) держит манифесты: они проверяются zod при импорте, поэтому нужны только серверным компонентам (каталог, метаданные, sitemap). Клиентские компоненты берут игры из `gameLoader` (`apps/web/src/game-loader`), а из `games` импортируют только тип `GameId` (`import type`). Иначе zod и все манифесты уезжают в JS каталога: на M0-05 это было +34 КБ gzip (174 → 140 КБ после разделения).
- **API остаётся в `apps/api`.** Route handlers Next не становятся вторым бэкендом. Допустимы только вещи, тесно связанные с рендером, например генерация OG-картинок.
- **Пакеты `@repo/*` отдают TS-исходники** — Next собирает их через `transpilePackages`.
- **Рантайм — Bun, Node не нужен.** Скрипты `web` запускают Next через `bun --bun` (без флага CLI Next стартует под Node из-за `#!/usr/bin/env node`). В Docker — образ `oven/bun` со standalone-сборкой (`bun server.js`). Так у всего монорепо один рантайм.
  - Проверено 2026-11-19 на Next 16.4.5 и Bun 1.4.5: `next build`, `next start`, `next dev` и standalone `server.js` работают под Bun.
  - `@types/node` нужен только как типы: Bun реализует Node API (Bun 1.4.5 сообщает `process.versions.node` = 26.12.1), поэтому версия `@types/node` следует за Bun — сейчас ветка 26.
  - Риск: Next официально тестируется на Node. Если обновление Next сломается под Bun, запасной вариант — убрать `--bun` из трёх скриптов и поставить Node; код не меняется. В CI будет smoke-проверка `next build` + `next start` под Bun.
- **`mountGame` и платформа (`GameContext`) — чистый TS без Next.** Фреймворк меняется только в слое страниц.

#### Бюджеты производительности

Проверяем Lighthouse с первого дня:

- каталог: LCP < 2,5 с (порог «хорошо» Core Web Vitals) в Lighthouse Mobile с симуляцией «Slow 4G», JS < 150 КБ gzip;
  - замер M0-05 (production-сборка Turbopack): 140 КБ, из них около 130 КБ — сам Next 16 и React 19, наш код каталога — 9 КБ. Бюджет защищает от того, что добавляем мы: каждый новый клиентский импорт на каталоге должен быть осознанным;
  - LCP на M0-05: 2,0 с в симуляции, 0,06 с реально (картинка рисуется первым кадром из готового HTML). Симуляция пересчитывает на Slow 4G все запросы, начатые до LCP, поэтому упирается в JS фреймворка: 1,5 с с Next недостижимы без отказа от гидрации каталога;
  - LCP-картинка (первая карточка) — `loading="eager"` + `fetchPriority="high"`, а не `preload`: иначе она грузится с низким приоритетом;
- игра: от клика «Играть» до первого кадра < 3 с на хорошем канале (чанк предзагружен при наведении).

## Структура репозитория

```
apps/
  web/            Next.js: /[locale] каталог, /[locale]/play/[id], профиль, лидерборды
  api/            auth, профили, очки, лидерборды
  game-server/    Colyseus: регистрирует комнаты из пакетов игр
packages/
  game-core/      контракт GameModule, цикл, ввод, ассеты, звук, Transport, сетевые хелперы
  game-protocol/  общие schema и типы сообщений Colyseus
  contracts/      zod-схемы API (общие для web и api)
  db/             Drizzle-схема и миграции
  auth/           конфиг Better Auth
  ui/             React-компоненты оболочки
games/
  <game>/         одна игра = один пакет @repo/game-<game>
```

Плоско, без группировки `2d/3d`: тип игры хранится в манифесте (`kind`), а не в пути.

### Имена пакетов

- Библиотеки из `packages/*`: `@repo/<name>` (`@repo/ui`, `@repo/game-core`, `@repo/contracts`).
- Игры из `games/*`: `@repo/game-<game>` (`@repo/game-bridge`).
- Приложения из `apps/*`: без scope — `web`, `api`, `game-server`. На эти имена ссылаются корневые скрипты.
- Все внутренние пакеты помечены `"private": true` и подключаются через `"workspace:*"`. `@repo` — локальное соглашение монорепо, в npm пакеты не публикуются.

`packages/` — это платформа: инфраструктура, которую используют все. `games/` — контент: конечные продукты, которые потребляют только `apps/web` и `apps/game-server`.

### Направление зависимостей

```
apps/*     →  games/*, packages/*
games/*    →  packages/*
packages/* →  только packages/*      (никогда games/*)
games/a    ✗→ games/b                (игры не знают друг о друге)
```

Правило проверяется по путям: grep в CI, lint-правило на импорты.

Workspaces: `["apps/*", "packages/*", "games/*"]`.

### Структура модуля внутри пакета

Код пакета делится на модули по смыслу: `src/<модуль>/`. Все модули устроены одинаково, файлы с фиксированными именами:

```
loop/
  index.ts        публичный API модуля: только реэкспорты
  type.ts         типы и интерфейсы
  schema.ts       zod-схемы (только если модуль проверяет внешние данные)
  loop.ts         реализация; файл называется как папка
  loop.test.ts    тесты рядом с реализацией
```

Правила:

- **Реализация называется как модуль** (`loop/loop.ts`, `manifest/manifest.ts`), а не как функция и не `impl.ts`. Тогда во вкладках редактора и в поиске по файлам сразу видно, о каком модуле речь.
- **Никаких папок по виду кода** (`functions/`, `utils/`, `helpers/`, `types/`) внутри модуля: они добавляют вложенность и со временем превращаются в свалку.
- **Если реализаций в модуле несколько, делим по смыслу:** `input/keyboard.ts` + `input/keyboard.test.ts`, `input-frame/codec.ts` + `input-frame/codec.test.ts`. Каждый такой файл называется по тому, _что_ он делает.
- **Снаружи модуля импортируем только через его `index.ts`.** Внутри модуля файлы импортируют друг друга напрямую.
- **Корневой `src/index.ts` пакета** реэкспортирует публичные `index.ts` модулей и больше ничего не содержит.
- **Расширение `.ts` в импортах обязательно**, импорт папки без расширения (`"../manifest"`) не используем.
- **Между модулями — алиас `#` из `package.json`** (Node subpath imports): `"imports": { "#*": "./src/*" }`, и `import { games } from "#games/index.ts"` вместо `"../../../../games/index.ts"`.
  - Алиас — только для импортов _между_ модулями, по-прежнему через `index.ts`. Внутри модуля и для файлов рядом с маршрутом (`./play-link.tsx`) импорты остаются относительными.
  - Почему не `paths` в `tsconfig.json` (`@/`): это настройка TypeScript, и Next берёт её только у приложения. Пакеты (`games/*`, `packages/*`) Next собирает из исходников через `transpilePackages`, и их `paths` ломают и сборку, и `typecheck` (проверено). `imports` разрешается относительно `package.json` пакета, где лежит файл, поэтому работает везде: Bun, Turbopack, TypeScript, у каждого пакета свои алиасы.
  - Форма `#games/...`, а не `#/games/...`: записи с `#/` Node долго считал недопустимыми, поддержка в инструментах неравномерная.
  - Сейчас алиас есть только у `apps/web`. Пакету он добавляется так же, когда в нём появятся глубокие импорты.

Исключение — `@repo/utils`: это набор независимых мелких функций, а не модули, поэтому там по файлу на функцию с именем функции (`is-slug.ts`, `is-slug.test.ts`).

### Стиль кода

Форматирование решает `bun fmt`, остальное — правила `bun lint` в `bunfig.toml`:

- **Тело `if`/`else`/цикла всегда в фигурных скобках** (`curly: all`), даже из одной строки: `if (!isLocale(current)) notFound();` запрещено. Без скобок вторая строка, добавленная под условием с тем же отступом, выполняется всегда. `bun lint --fix` расставляет скобки сам.
- **Значения и типы экспортируются отдельными строками:** `export { a }` и `export type { B }` (`typescript/consistent-type-exports`).
- **Неиспользуемые переменные и импорты — ошибка** (`typescript/no-unused-vars`).

## Контракт игры

Каждая игра — отдельный пакет. Контракт состоит из двух сущностей:

- **`GameManifest`** — паспорт игры: `id`, `title`, `kind`, `thumbnail`, параметры мультиплеера. Это лёгкие статические данные без кода. Оболочка импортирует манифесты всех игр сразу, для каталога.
- **`GameModule`** — сама игра: манифест плюс `mount()`, за которым стоят движок, физика и ассеты. Оболочка грузит модуль лениво, только при открытии игры.

```ts
interface GameModule {
  manifest: GameManifest;
  mount(el: HTMLElement, ctx: GameContext): Promise<Unmount>;
}
```

Оба создаются через хелперы из `@repo/game-core`:

```ts
// games/bridge/src/manifest.ts — вход ./manifest
export const manifest = defineManifest({ id: "bridge", title: "Bridge", kind: "3d", thumbnail: "…" });

// games/bridge/src/client/index.ts — вход ./client
import { manifest } from "../manifest.ts";
export default defineGame({ manifest, mount: async (el, ctx) => { … } });
```

- `defineManifest` проверяет манифест схемой в момент импорта (и в каталоге, и в игре) и сохраняет литеральные типы (`id: "bridge"`, а не `string`).
- `defineGame` только оборачивает `mount`, чтобы возвращённый `Unmount` был идемпотентным.
- Оболочка импортирует только `@repo/game-<game>/manifest` (статически, для каталога), а `@repo/game-<game>/client` грузит лениво через `import()`. Бандл режется на чанки, и Three.js не грузится ни на странице каталога, ни для 2D-игр.
- `unmount` обязан освободить всё: `renderer.dispose()`, `forceContextLoss()`, слушатели, Worker'ы, соединения. Иначе при переходах между играми утекают WebGL-контексты.
- `GameContext` даёт игре пользователя, настройки, `submitScore` и фабрику `Transport`.

### Раскладка пакета игры

```
games/bridge/
  package.json   "@repo/game-bridge"
  src/
    manifest.ts
    sim/       чистый TS + физика: мир, команды, правила, подсчёт очков. Без DOM и рендера
    server/    комната Colyseus: обёртка над sim, машина состояний, матчмейкинг
    bots/      ИИ, выдаёт те же команды, что и игрок
    client/    рендер, ввод, предсказание и интерполяция, камера, HUD
  levels/      уровни (JSON)
  assets/      glTF, текстуры KTX2, meshopt, звук (кандидат на Git LFS)
```

Правило: `sim/` импортируют и `client/`, и `server/`, а сам `sim/` не импортирует ни того, ни другого.

Пакет игры открывает наружу только три входа:

```jsonc
"exports": {
  "./manifest": "./src/manifest.ts",     // web: каталог (лёгкий, без three)
  "./client":   "./src/client/index.ts", // web: ленивый import()
  "./server":   "./src/server/index.ts"  // game-server: регистрация комнаты
}
```

Входа на `./sim` нет намеренно: симуляцию используют только `client` и `server` изнутри пакета.

**Граница `sim/` (решено в M0-06, вариант А):** один пакет на игру, у `src/sim` свой `tsconfig.json` без DOM (подключён в `references` корневого `tsconfig.json`), поэтому `document` или `window` в `sim` роняют `bun run typecheck`. Импорты сторожит `src/sim/boundary.test.ts`: разрешены только свои файлы и `@repo/game-protocol`, а `three`, `../client` и `@repo/game-core` (DOM-ввод, цикл на `requestAnimationFrame`) роняют `bun test`. Вариант Б (три пакета на игру) отложен: граница жёстче, но шаблонного кода втрое больше.

### Transport

Игра общается с «сервером» через интерфейс `Transport`. У него две реализации:

- `ColyseusTransport` — настоящий сервер.
- `LocalTransport` — та же логика комнаты в Web Worker. Используется для одиночной игры против CPU и офлайн-отладки.

Поэтому одиночный режим и мультиплеер используют один и тот же код правил.

## Сетевая модель (realtime-игры)

- Авторитарный сервер с фиксированным тиком: симуляция 30 Гц, снапшоты 15–20 Гц.
- Данные делятся на три вида:
  1. **Свой аватар.** Предсказание на клиенте, сверка с сервером по `inputSeq`.
  2. **Чужие сущности.** Интерполяция с буфером около 100 мс. Бинарные снапшоты (`sendBytes`): позиции и кватернионы квантованы, спящие тела не отправляются.
  3. **Дискретные действия.** Команды проверяются и применяются сервером. Клиент сразу показывает оптимистичный «призрак», который заменяется подтверждённым состоянием.
- Мета-состояние (фаза, игроки, очки, таймер) передаётся через Colyseus schema.
- Очки считаются только на сервере.

## Матчмейкинг и идентификация

- **Комната по коду:** `create({ private: true })`, код из 6 символов хранится в Redis presence и сопоставляется с `roomId`. Ссылка: `/play/<game>?room=K7X2QP`.
- **Быстрая игра:** `joinOrCreate` с фильтрами по режиму и сложности. Если за N секунд комната не набралась, свободные места занимают боты.
- **Гости:** при первом заходе выдаётся анонимная сессия Better Auth. Её токен проверяется в `onAuth` комнаты. Анонимный аккаунт можно позже привязать к настоящему.

## Хранение данных на клиенте

Решение от 2026-11-19. Хранилище выбираем по тому, кто читает данные и сколько они должны жить.

| Данные                                              | Сейчас (M0)                                                      | В итоге                                                        | Почему                                                                            |
| --------------------------------------------------- | ---------------------------------------------------------------- | -------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| Громкость, качество, `reducedMotion`                | `localStorage`                                                   | `localStorage` (позже — синхронизация с аккаунтом через API)   | нужны только в браузере; в cookie зря уходили бы с каждым запросом                |
| Язык                                                | сегмент URL `app/[locale]`, читается через `next/root-params`    | то же + cookie для запоминания выбора                          | серверу нужен для рендера и SEO; у каждой языковой версии свой URL                |
| Идентичность игрока                                 | id гостя в `localStorage` (заглушка, сервер ему **не доверяет**) | `HttpOnly`, `Secure`, `SameSite=Lax` cookie сессии Better Auth | токен недоступен JS (защита от XSS), браузер сам шлёт его в `api` и `game-server` |
| Состояние одной вкладки (например, текущая комната) | —                                                                | `sessionStorage`                                               | живёт, пока открыта вкладка, у каждой вкладки своё                                |

Правила:

- **`sessionStorage` не используем для настроек и идентичности:** он очищается при закрытии вкладки и у каждой вкладки свой.
- **Токены и сессии — никогда в `localStorage`:** при XSS он читается целиком.
- **Язык — в URL, а не в cookie.** Если серверный компонент читает `cookies()`, страница становится динамической, и теряется SSG. Root params (`app/[locale]/layout.tsx` + `generateStaticParams`) сохраняют статический рендер.
  - Root params доступны только в серверных компонентах. Клиентские получают язык через props от серверной страницы.
  - `/` перенаправляет на язык по умолчанию: в M0 статическим `redirects()` в `next.config.ts`, позже — в `proxy.ts` (бывший middleware) с учётом cookie выбора и `Accept-Language`.
- **`localStorage` и cookie — граница доверия:** всё прочитанное оттуда проверяем схемой (zod) и при ошибке откатываемся к значению по умолчанию.
- **Доступ к хранилищу — через `KeyValueStorage`** (`apps/web/src/platform`). Игры не обращаются к `localStorage` напрямую и получают данные только через `GameContext`.
- Настройки интерфейса и сессия входа — «строго необходимые» данные, баннер согласия для них не нужен. Он понадобится только для аналитики или рекламы.

## Первая игра: bridge

Оригинальная игра: свои название, персонажи, арт и уровни. Жанр — физическая гонка по стройке моста.

- **Полное 3D.** Аватар ходит по площадке, носит доски и прибивает их гвоздями.
- **Управление:** WASD — движение, захват и отпускание, поворот, гвоздь, пауза. Раскладка переназначаемая.
- **Вращение с привязкой** (шаг 15°) и сетка для гвоздей. Это упрощает управление, сверку с чертежом, стабильность физики и трафик.
- **Гвозди** — joint'ы Rapier плюс своя логика поломки: каждый тик меряем деформацию соединения и разрываем его, если превышен порог.
- **Фазы матча:** `lobby → countdown → build → loadTest → results → (rematch | lobby)`.
- **Очки:** время, прочность (нагрузочный тест) и совпадение с чертежом.
- **Режимы:**
  - Гонка: у каждого свой мост, физика игроков не пересекается (отдельные миры или группы коллизий).
  - Кооп: один общий мост и общий мир. Взятая доска блокируется за игроком.
  - Одиночная игра против CPU через `LocalTransport`.
- 2–8 игроков в комнате. Вход по коду или ссылке и через быструю игру.
