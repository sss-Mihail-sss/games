# Архитектура games.secrii.dev

Сайт с несколькими браузерными 2D/3D-играми. Игры пишутся одним автором (3–10 штук), платформа — десктоп.

## Принятые решения

| Вопрос          | Решение                                                             |
| --------------- | ------------------------------------------------------------------- |
| Мультиплеер     | Соревновательный realtime, авторитарный сервер (Colyseus)           |
| Аккаунты        | Гость по умолчанию + опциональный аккаунт                           |
| Встраивание игр | Прямо в страницу (`mount/unmount`), без iframe                      |
| Платформы       | Десктоп: клавиатура, мышь, геймпад. Тач и PWA не нужны              |
| Первая игра     | Оригинальная 3D-гонка по стройке мостов (рабочее название `bridge`) |

## Стек

| Слой              | Технология                                                           |
| ----------------- | -------------------------------------------------------------------- |
| Рантайм, монорепо | Bun workspaces                                                       |
| Оболочка сайта    | React 19, Bun HTML imports, `Bun.serve`                              |
| 2D                | Phaser 4 (или PixiJS 8, если нужен только рендер)                    |
| 3D                | Three.js (WebGPURenderer с откатом на WebGL2), без R3F               |
| Физика            | Rapier (WASM), одна и та же в браузере и на сервере                  |
| Realtime          | Colyseus 0.18 + `@colyseus/bun-websockets`                           |
| API               | `Bun.serve` routes, zod-схемы в `packages/contracts`                 |
| БД                | Postgres через `Bun.sql` + Drizzle                                   |
| Кэш, presence     | Redis (`Bun.redis`), Colyseus RedisPresence                          |
| Авторизация       | Better Auth: анонимные сессии + аккаунты                             |
| Деплой            | Docker Compose на VPS: Caddy, web, api, game-server, Postgres, Redis |

### API: чистый Bun, а не Elysia 2 RC

Решение от 2026-11-18: `apps/api` пишем на `Bun.serve` без фреймворка.

- API тонкий: авторизация, профили, очки, лидерборды — порядка десятка эндпоинтов. Игровой трафик идёт через Colyseus, а не через API, так что производительность и богатый middleware здесь не нужны.
- RC в фундаменте — лишний риск: API может поменяться до релиза, документация и экосистема плагинов отстают.
- Всё нужное есть в Bun: `routes` с параметрами, `Request`/`Response`. Better Auth монтируется одной строкой (`"/api/auth/*": req => auth.handler(req)`).
- Типобезопасность клиент ↔ сервер даёт `packages/contracts`: zod-схемы запросов и ответов общие для `web` и `api`. Это заменяет Eden Treaty из Elysia.
- Что пишем сами (маленький модуль в `apps/api/src/http/`): валидация тела и query через zod-схему из `contracts`, единый формат ошибок, CORS, логирование запросов.

**Когда пересмотреть:** если понадобятся OpenAPI-документация, много middleware или эндпоинтов станет больше 30–40. К тому времени Elysia 2 выйдет из RC. Миграция дешёвая: обработчики тонкие, а zod-схемы из `contracts` Elysia принимает через Standard Schema.

## Структура репозитория

```
apps/
  web/            оболочка: каталог, /play/:id, профиль, лидерборды
  api/            auth, профили, очки, лидерборды
  game-server/    Colyseus: регистрирует комнаты из пакетов игр
packages/
  game-core/      контракт GameModule, цикл, ввод, ассеты, звук, Transport, сетевые хелперы
  game-protocol/  общие schema и типы сообщений Colyseus
  contracts/      zod-схемы API (общие для web и api)
  db/             Drizzle-схема и миграции
  auth/           конфиг Better Auth
  ui/             React-компоненты оболочки
games/
  <game>/         одна игра = один пакет @repo/game-<game>
```

Плоско, без группировки `2d/3d`: тип игры хранится в манифесте (`kind`), а не в пути.

### Имена пакетов

- Библиотеки из `packages/*`: `@repo/<name>` (`@repo/ui`, `@repo/game-core`, `@repo/contracts`).
- Игры из `games/*`: `@repo/game-<game>` (`@repo/game-bridge`).
- Приложения из `apps/*`: без scope — `web`, `api`, `game-server`. На эти имена ссылаются корневые скрипты.
- Все внутренние пакеты помечены `"private": true` и подключаются через `"workspace:*"`. `@repo` — локальное соглашение монорепо, в npm пакеты не публикуются.

`packages/` — это платформа: инфраструктура, которую используют все. `games/` — контент: конечные продукты, которые потребляют только `apps/web` и `apps/game-server`.

### Направление зависимостей

```
apps/*     →  games/*, packages/*
games/*    →  packages/*
packages/* →  только packages/*      (никогда games/*)
games/a    ✗→ games/b                (игры не знают друг о друге)
```

Правило проверяется по путям: grep в CI, lint-правило на импорты.

Workspaces: `["apps/*", "packages/*", "games/*"]`.

## Контракт игры

Каждая игра — отдельный пакет, который экспортирует манифест и `GameModule`:

```ts
interface GameModule {
  manifest: GameManifest;
  mount(el: HTMLElement, ctx: GameContext): Promise<() => void>; // возвращает unmount
}
```

- Оболочка импортирует только `@repo/game-<game>/manifest` (статически, для каталога), а `@repo/game-<game>/client` грузит лениво через `import()`. Бандл режется на чанки, и Three.js не грузится ни на странице каталога, ни для 2D-игр.
- `unmount` обязан освободить всё: `renderer.dispose()`, `forceContextLoss()`, слушатели, Worker'ы, соединения. Иначе при переходах между играми утекают WebGL-контексты.
- `GameContext` даёт игре пользователя, настройки, `submitScore` и фабрику `Transport`.

### Раскладка пакета игры

```
games/bridge/
  package.json   "@repo/game-bridge"
  src/
    manifest.ts
    sim/       чистый TS + физика: мир, команды, правила, подсчёт очков. Без DOM и рендера
    server/    комната Colyseus: обёртка над sim, машина состояний, матчмейкинг
    bots/      ИИ, выдаёт те же команды, что и игрок
    client/    рендер, ввод, предсказание и интерполяция, камера, HUD
  levels/      уровни (JSON)
  assets/      glTF, текстуры KTX2, meshopt, звук (кандидат на Git LFS)
```

Правило: `sim/` импортируют и `client/`, и `server/`, а сам `sim/` не импортирует ни того, ни другого.

Пакет игры открывает наружу только три входа:

```jsonc
"exports": {
  "./manifest": "./src/manifest.ts",     // web: каталог (лёгкий, без three)
  "./client":   "./src/client/index.ts", // web: ленивый import()
  "./server":   "./src/server/index.ts"  // game-server: регистрация комнаты
}
```

Входа на `./sim` нет намеренно: симуляцию используют только `client` и `server` изнутри пакета.

**Открытый вопрос (решаем в M1):** как обеспечить, что `sim/` не видит DOM. Вариант А — один пакет на игру и отдельные tsconfig для `src/sim` (без DOM) и `src/client` (с DOM). Вариант Б — три пакета на игру (`games/<game>/{sim,client,server}`): граница жёстче, но шаблонного кода втрое больше. Сейчас склоняемся к варианту А.

### Transport

Игра общается с «сервером» через интерфейс `Transport`. У него две реализации:

- `ColyseusTransport` — настоящий сервер.
- `LocalTransport` — та же логика комнаты в Web Worker. Используется для одиночной игры против CPU и офлайн-отладки.

Поэтому одиночный режим и мультиплеер используют один и тот же код правил.

## Сетевая модель (realtime-игры)

- Авторитарный сервер с фиксированным тиком: симуляция 30 Гц, снапшоты 15–20 Гц.
- Данные делятся на три вида:
  1. **Свой аватар.** Предсказание на клиенте, сверка с сервером по `inputSeq`.
  2. **Чужие сущности.** Интерполяция с буфером около 100 мс. Бинарные снапшоты (`sendBytes`): позиции и кватернионы квантованы, спящие тела не отправляются.
  3. **Дискретные действия.** Команды проверяются и применяются сервером. Клиент сразу показывает оптимистичный «призрак», который заменяется подтверждённым состоянием.
- Мета-состояние (фаза, игроки, очки, таймер) передаётся через Colyseus schema.
- Очки считаются только на сервере.

## Матчмейкинг и идентификация

- **Комната по коду:** `create({ private: true })`, код из 6 символов хранится в Redis presence и сопоставляется с `roomId`. Ссылка: `/play/<game>?room=K7X2QP`.
- **Быстрая игра:** `joinOrCreate` с фильтрами по режиму и сложности. Если за N секунд комната не набралась, свободные места занимают боты.
- **Гости:** при первом заходе выдаётся анонимная сессия Better Auth. Её токен проверяется в `onAuth` комнаты. Анонимный аккаунт можно позже привязать к настоящему.

## Первая игра: bridge

Оригинальная игра: свои название, персонажи, арт и уровни. Жанр — физическая гонка по стройке моста.

- **Полное 3D.** Аватар ходит по площадке, носит доски и прибивает их гвоздями.
- **Управление:** WASD — движение, захват и отпускание, поворот, гвоздь, пауза. Раскладка переназначаемая.
- **Вращение с привязкой** (шаг 15°) и сетка для гвоздей. Это упрощает управление, сверку с чертежом, стабильность физики и трафик.
- **Гвозди** — joint'ы Rapier плюс своя логика поломки: каждый тик меряем деформацию соединения и разрываем его, если превышен порог.
- **Фазы матча:** `lobby → countdown → build → loadTest → results → (rematch | lobby)`.
- **Очки:** время, прочность (нагрузочный тест) и совпадение с чертежом.
- **Режимы:**
  - Гонка: у каждого свой мост, физика игроков не пересекается (отдельные миры или группы коллизий).
  - Кооп: один общий мост и общий мир. Взятая доска блокируется за игроком.
  - Одиночная игра против CPU через `LocalTransport`.
- 2–8 игроков в комнате. Вход по коду или ссылке и через быструю игру.

## Этапы

| Этап | Содержание                                                                                              |
| ---- | ------------------------------------------------------------------------------------------------------- |
| M0   | Чистка монорепо, контракт `game-core`, оболочка `web` с `/play/:id`, заглушка `bridge`                  |
| M1   | Песочница в браузере: аватар, доски, гвозди, нагрузочный тест. Проверяем, что весело и физика стабильна |
| M2   | Комната Colyseus, гонка на 2–8 игроков, комнаты по коду                                                 |
| M3   | Быстрая игра, боты, подсчёт очков, экран результатов                                                    |
| M4   | Кооп на общем мосту                                                                                     |
| M5   | Аккаунты, лидерборды, история матчей                                                                    |

Хостинг выбираем к M2. Redis presence закладываем с самого начала, чтобы позже можно было масштабироваться на несколько серверов и регионов.
