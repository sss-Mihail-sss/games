# Задачи

Архитектура описана в [ARCHITECTURE.md](../ARCHITECTURE.md).

## Как работаем

1. Берёшь следующую задачу из списка ниже и создаёшь ветку `m0-01-repo-hygiene` (ID и короткое имя).
2. Делаешь задачу, отмечаешь чекбоксы в её файле, коммитишь. PR открываешь **черновиком** (draft): черновик значит «работа в ветке ещё идёт».
3. Пишешь в чат «готово M0-01». Я смотрю `git diff main...<ветка>`, запускаю проверки и оставляю замечания со ссылками на `файл:строка`.
4. По результату ревью:
   - ✅ — переводишь PR в Ready for review, ждёшь зелёный `ci`, мержишь в `main` и берёшь следующую задачу;
   - 🔁 — правишь замечания в той же ветке и снова пишешь «готово».

**Правила для `main`.** Репозиторий публичный, поэтому GitHub применяет ruleset `main`:

- в `main` — только через PR, прямой пуш, force-push и удаление ветки запрещены;
- обязательна проверка `ci` ([workflow](../../.github/workflows/ci.yml)), а ветка должна быть актуальной относительно `main` («up to date»).

И одна договорённость, которую никакое правило не закрывает: **вливаем только PR, переведённый из черновика в Ready for review.** Дважды (#5, #11) PR влили, пока в ветку ещё шёл пуш, и коммит терялся. Оба PR были зелёными, так что блокировка по CI бы не помогла.

Если застрял больше чем на полчаса или хочешь отойти от архитектуры, пиши сразу, не жди ревью. Отклоняться можно, но с аргументами: если решение окажется лучше, обновим `ARCHITECTURE.md`.

## Definition of Done (для любой задачи)

- [ ] `bun check` без ошибок
- [ ] `bun test` зелёный, на новую логику есть тесты (кроме чистого рендера)
- [ ] `bun lint` без замечаний, `bun fmt --check` проходит
- [ ] В консоли браузера нет ошибок и предупреждений
- [ ] Нет закомментированного кода, отладочных `console.log` и `any` без комментария, зачем он нужен
- [ ] CI на PR зелёный
- [ ] Все чекбоксы в файле задачи отмечены или явно перенесены

## M1 — песочница

**Цель этапа** (ARCHITECTURE.md, «Этапы»): одиночная песочница в браузере. Аватар носит доски, прибивает их гвоздями, по мосту едет нагрузка. Отвечаем на два вопроса: **весело ли это** и **стабильна ли физика**. Сети ещё нет, но всё пишется так, чтобы в M2 тот же `sim` работал на сервере.

**Как поймём, что M1 готов** — плейтест:

- мост через провал из стопки досок собирается за 3–5 минут;
- нагрузка либо проезжает, либо мост ломается так, что видно где и почему;
- ничего не «взрывается»: нет улетающих досок, дрожания стоящих конструкций и проваливания сквозь берег;
- 60 FPS на среднем ноутбуке при 50 досках и 100 гвоздях.

Тикеты расписываются подробно по одному, перед началом. Ниже — план, порядок и что решаем в каждом.

### Решения, которые принимаем в M1

1. **Сборка Rapier — решено в [M1-01](M1-01-rapier-spike.md):** `@dimforge/rapier3d-deterministic-compat` 0.21.0. Хеш состояния после 600 шагов одинаковый в Bun на macOS arm64 и Linux x64 и в Chromium; обычная сборка дала тот же хеш, но детерминированная не медленнее и не тяжелее, так что гарантию берём бесплатно. Шаг при 50 досках и 100 соединениях — ~0,25 мс.
2. **Загрузка WASM — решено в [M1-01](M1-01-rapier-spike.md):** compat-сборка, WASM внутри JS, `await RAPIER.init()` один раз на страницу. Чанк игры с Rapier — ~1,75 МБ gzip. Сборка без compat (WASM отдельным файлом, −600 КБ gzip) работает в Turbopack, но не под Bun — откладываем до M1-08.
3. **`sim` перестаёт быть чистой функцией — сделано в [M1-02](M1-02-physics-world.md), форма описана в ARCHITECTURE.md.** Мир Rapier изменяемый, поэтому `step(state) → state` уступает место объекту `world.step(frame)` и паре `snapshot()` / `restore()` поверх `world.takeSnapshot()`. Снимки нужны для тестов («одни и те же кадры → одинаковый снимок»), для отката в предсказании M2 и для интерполяции: рендер берёт позиции из двух последних состояний. Граница `sim` расширяется: `boundary.test.ts` и `tsconfig` разрешают пакет Rapier.
4. **Частота физики (M1-02, M1-05).** Тик протокола остаётся 30 Гц, но гвоздям на 30 Гц может не хватить устойчивости. Варианты: несколько подшагов физики на тик или тик 60 Гц. Решаем по стабильности стоящей конструкции. Предварительно по M1-01: при `1/30` стопка досок «плывёт» ещё секунду после падения, при двух подшагах по `1/60` успокаивается сразу.
5. **Прицел — сделано в [M1-03](M1-03-mouse-aim.md).** Чтобы прибить гвоздь, нужно куда-то смотреть, а значит нужен `pitch`. Мышь переезжает в `createInput` (pointer lock), `InputFrame` v3 получает `pitch` по той же схеме квантования, что и `yaw`. Луч прицела считается в `sim`, чтобы сервер видел то же, что игрок.
6. **Рендерер (M1-08).** Остаёмся на `WebGLRenderer`, пока замеры не покажут, что упираемся в CPU рендера. Тогда обсуждаем WebGPU.
7. **Механики и способности живут в `sim` — сделано в [M1-09](M1-09-movement-abilities.md): `createSim(R, { abilities, stats, level })`, `sim.setAbilities()`.** Прыжок, спринт, присед и «крадучись» — действия ввода, добавленные **в конец** `defineActions` (порядок битов — протокол); прыжок — по биту `pressed`, остальное — по `held`. Что игроку доступно, решает `sim`, а не клиент:
   - набор способностей приходит снаружи, при создании мира: в M5 его определяет сервер по уровню и прокачке аккаунта, до этого — константа;
   - внутри матча его меняют правила игры (подобрал предмет — появился спринт; несёшь доску — нельзя прыгать);
   - выключенная способность — `sim` **игнорирует** действие. Это и есть защита: клиент только прячет кнопку и показывает «нужен уровень N»;
   - способности — часть состояния `sim` и снимка, иначе откат в M2 разойдётся.
8. **Модель — только картинка ([M1-10](M1-10-assets-avatar.md)).** Физика остаётся на примитивах из чисел в `sim` (капсула, кубы); сервер glTF не грузит. Анимации аватара — клиентские, выбираются маленьким автоматом состояний по `SimState` (скорость, `grounded`, присед). Соглашения для моделей: метры, начало координат у ног, «вперёд» — −Z. Арт свой или CC0 с проверенной лицензией.
9. **Персонажи — данные игры, а не платформы (M1-11).** У каждой игры свои персонажи и свой набор характеристик: в bridge это скорость, прыжок, сила (сколько досок несёшь, как быстро забиваешь гвоздь), в другой игре — что-то своё. Поэтому:
   - **описание персонажа — в `sim` игры**, чистыми данными без Rapier и `three`: `id`, имя, характеристики и способности, которые даёт персонаж. Характеристики — множители к базовым константам `sim` (например, `walkSpeed: 1.15`), а не абсолютные числа, чтобы баланс правился в одном месте;
   - **выбранный персонаж — часть настройки мира:** `createSim(R, { character, abilities })`. Всё, что влияет на физику (размер капсулы, скорость, сила), считает `sim`, поэтому сервер в M2 проверит то же самое;
   - **модель персонажа — только в клиенте:** `id` персонажа → свой `.glb` и анимации (M1-10);
   - **доступность** (уровень, покупка, предметы) решается как у способностей (решение 7): набор доступных персонажей приходит снаружи, в M5 — с сервера по аккаунту;
   - **последний выбор** запоминается для каждой игры отдельно — через хранилище игры в `GameContext`, которое появляется в M1-12 (решение 10);
   - **экран выбора** — в игре, а не в оболочке: каталог про персонажей не знает. В M2 выбор переедет в лобби комнаты, и сервер проверит, что персонаж игроку доступен.

10. **Меню и настройки: общие — у платформы, клавиши — у игры; меню и экран настроек рисует платформа (M1-12).**
    - **Общие для всех игр** — в `PlatformSettings`: громкость (общая, музыка, эффекты), мышь (чувствительность, инверсия), качество графики, `reducedMotion`, язык и новое **поле зрения (FOV)**, например 60–100°. FOV — вопрос комфорта игрока (укачивание), а не правило игры.
    - **Свои у каждой игры** — назначение клавиш: у каждой игры свои действия. Хранятся в **хранилище игры** — новом контракте `GameContext` (ключи с префиксом `id` игры; сначала `localStorage`, после M5 — аккаунт). Им же пользуются персонажи (M1-11) и любые другие локальные данные игры.
    - **Игра объявляет, платформа рисует:** игра отдаёт список действий с подписями и раскладку по умолчанию, а платформа показывает один общий экран (громкость, мышь, FOV, «Клавиши этой игры»). Каждой игре не нужно писать свой экран настроек.
    - **Изменения применяются на лету** через `settings.subscribe`: FOV — `camera.fov` + `updateProjectionMatrix()`, раскладка — `input.setBindings()`.
    - **Главное меню игры** — первое, что видит игрок на `/play/<id>` вместо «Кликни, чтобы играть»: «Играть», «Персонаж» (M1-11), «Настройки», «В каталог»; в M2 добавятся «Комната по коду» и «Быстрая игра». Мир и физика грузятся, пока открыто меню, поэтому «Играть» срабатывает сразу.
    - **Меню паузы** — по Esc (он и так отпускает мышь): «Продолжить», «Настройки», «В главное меню». В одиночной игре пауза останавливает цикл (`loop.stop()`); в мультиплеере (M2) матч на сервере не останавливается — меню просто закрывает экран, а ввод перестаёт уходить.
    - **Кто рисует.** Общий каркас меню (кнопки, фокус с клавиатуры, анимации, стиль сайта) — платформа: одинаковый во всех играх и написан один раз на React в оболочке. Игра объявляет свои пункты (например, «Персонаж» или режимы) и реагирует на события: «начать», «пауза», «продолжить», «выйти». Это расширение контракта `GameContext` / `GameModule`, а не DOM внутри игры, как сейчас оверлей M1-03.
    - **Экран настроек** открывается из главного меню, из меню паузы и из каталога (только общие настройки — там нет игры).
    - **Клавиши:** храним `KeyboardEvent.code` (физическая клавиша); подписи — через `navigator.keyboard.getLayoutMap()` там, где он есть; конфликт двух действий на одной клавише — предупреждение с выбором «заменить»; Esc занять нельзя; «Сбросить к стандартным».
