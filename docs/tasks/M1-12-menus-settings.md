# M1-12 · Меню и настройки

## Цель

Сейчас игра открывается сразу в мир с надписью «Кликни, чтобы играть». Настроек в интерфейсе нет совсем, а клавиши жёстко прописаны в клиенте bridge. Нужно:

- **главное меню игры** — первое, что видит игрок на `/play/<id>`: «Играть», «Настройки», «В каталог». Мир и физика грузятся, пока открыто меню, поэтому «Играть» срабатывает сразу;
- **меню паузы** по Esc: «Продолжить», «Настройки», «В главное меню»;
- **экран настроек:**
  - **общие для всех игр:** громкость, мышь, графика, новое поле зрения (FOV);
  - **свои у каждой игры:** назначение клавиш;
- **хранилище игры** в `GameContext`: место для данных игры в браузере. Первыми им воспользуются клавиши, затем выбор персонажа в M1-11.

Всё это — решение 10 в `docs/tasks/README.md`. Главная мысль: **игра объявляет, платформа рисует.** Игра сообщает, какие у неё действия и клавиши по умолчанию, и реагирует на «начать / пауза / продолжить». Меню и экран настроек — один общий React-код в оболочке, одинаковый для всех игр. Ни одна игра не пишет свой экран настроек.

## Перед началом

- **Сначала слей M1-10 ([#24](https://github.com/sss-Mihail-sss/games/pull/24)).** Он переписывает начало `mount` в `games/bridge/src/client/index.ts` (загрузка модели, `loop.start()` в конце). M1-12 меняет то же место: цикл стартует по «Играть», а не сразу. Начнёшь раньше — будет конфликт в самом важном файле.
- Тикет большой, поэтому делай три коммита в одном PR, по частям ниже: **A** — контракт и логика платформы (без React), **B** — реакция bridge, **C** — интерфейс. После A и B игра ещё запускается по клику на canvas, как сейчас: временно сделай так, чтобы до появления меню (C) состояние сразу было `playing`.

## Что сделать

### Часть A · Контракт и логика платформы

#### 1. FOV в `PlatformSettings`

- [x] `PlatformSettings.fov: number` — **горизонтальный** угол в градусах для экрана 16:9, диапазон `70…110`, по умолчанию `90`. Так FOV задают почти все игры, и игрок сравнивает с привычными числами.
- [x] В `settings.ts`: значение по умолчанию и zod-схема с `.catch`, как у остальных полей. Число вне диапазона из `localStorage` — значение по умолчанию, как у громкости: сохранённые 500° — мусор, а не желание видеть шире всех.
- [x] Чистая функция для клиента: `verticalFov(horizontalDegrees)` → вертикальный угол для `PerspectiveCamera.fov`:
      `v = 2·atan(tan(h/2) · 9/16)`. При 90° получается ≈ 58,7°, почти как сейчас (60°), поэтому по умолчанию картинка не изменится.
  - Положи её в клиент bridge, а не в `sim`: FOV — вопрос комфорта, а не правило игры. Сервер о нём не знает.
  - Вертикальный угол фиксирован, а ширина растёт с экраном («Hor+»). Это `PerspectiveCamera` делает сама через `aspect`: на широком мониторе видно больше по бокам, а не меньше сверху и снизу.
- [x] Тесты: 90° → 58,72° (±0,01), функция монотонна, границы `70` и `110`.

#### 2. Один `SettingsStore` на страницу и синхронизация вкладок

Сейчас `GameHost` создаёт свой store в `useEffect`. Экрану настроек нужен тот же экземпляр: подвинул слайдер — игра сразу видит изменение через `subscribe`.

- [x] Один store на страницу: `browserSettings()` в `platform/browser.ts` создаёт его при первом вызове на клиенте. `GameHost` и экран настроек берут его оттуда. Провайдер в layout не понадобился: store живёт столько же, сколько страница.
- [ ] Для React (часть C, где появится первый компонент с настройками) — `useSyncExternalStore(store.subscribe, () => store.current, () => DEFAULT_SETTINGS)`. Третий аргумент — снимок для сервера: на сервере `localStorage` нет, поэтому HTML строится со значениями по умолчанию, а настоящие подставляются после гидратации.
- [x] **Две вкладки:** store слушает событие `storage` у `window` для ключа `games:settings`. Изменил громкость в одной вкладке — во второй она обновилась без перезагрузки. Не забудь отписку.
- [x] Тесты store: событие `storage` с битым JSON не роняет store и не зовёт подписчиков с мусором.

#### 3. Хранилище игры: `GameContext.storage`

- [x] В `@repo/game-core`:

  ```ts
  export interface GameStorage {
    /** Разобранный JSON или undefined. Проверяй схемой: игрок может отредактировать localStorage. */
    get(key: string): unknown;
    set(key: string, value: unknown): void;
    remove(key: string): void;
  }
  ```

  `GameContext.storage: GameStorage`.

- [x] В платформе — `createGameStorage(storage, gameId)`:
  - ключи — `games:<id>:data:<key>`, чтобы две игры не видели данные друг друга и не пересекались с ключами платформы;
  - битый JSON — `undefined`, а не исключение;
  - `KeyValueStorage` получает `remove`; `createBrowserStorage` глотает ошибки и тут, как в `get` и `set`.
- [x] Тесты:
  - круговой путь `set` → `get`;
  - две игры с одинаковым ключом не мешают друг другу;
  - битое значение → `undefined`;
  - `remove`.

#### 4. Управление, которое объявляет игра

- [x] В `@repo/game-core` — описание управления:

  ```ts
  export interface Controls<A extends readonly string[]> {
    /** Порядок — порядок строк на экране «Клавиши». */
    actions: A;
    /** Подписи по-русски; переводы — когда появится второй язык. */
    labels: Record<A[number], string>;
    /** До двух клавиш на действие: основная и дополнительная. */
    defaults: Bindings<A>;
  }
  ```

  `defineGame({ manifest, controls, mount })` и `GameModule.controls?`. Без `controls` игра просто не показывает вкладку «Клавиши».

- [x] В платформе — хранилище раскладки `createBindingsStore(storage, gameId, controls)`:
  - ключ `games:<id>:bindings` — платформенный, рядом с `data:` игры, но не внутри него;
  - **при загрузке** раскладка проверяется по `controls`:
    - неизвестные действия и источники выбрасываются;
    - запрещённые клавиши (ниже) выбрасываются;
    - больше двух клавиш — лишние отбрасываются;
  - **действие, которого нет в сохранённой раскладке** (игра добавила новое), получает клавиши по умолчанию. Если клавиша уже занята другим действием игрока, действие остаётся **без клавиши**: не отнимай клавишу, которую игрок назначил сам;
  - `current`, `subscribe`, `assign(action, slot, code)`, `clear(action, slot)`, `reset()`.
- [x] **Конфликты — чистая функция**, без DOM: `assign` на клавишу, занятую другим действием, не применяет изменение, а возвращает `{ conflict: "jump" }`. Интерфейс спрашивает «Заменить?», и только тогда вызывается `assign(..., { replace: true })`: клавиша уходит из старого действия. Та же клавиша в двух слотах одного действия — ничего не делать.
- [x] **Запрещённые клавиши:**
  - `Escape` — браузер всегда отдаёт его выходу из захвата мыши;
  - `ControlLeft/Right`, `AltLeft/Right`, `MetaLeft/Right` — `Ctrl+W` закрывает вкладку, `Alt` уводит фокус в меню окна, `Meta` занят ОС (это уже решили в M1-09);
  - `F1`…`F12` — справка, перезагрузка, полноэкранный режим, инструменты разработчика;
  - `CapsLock` — на macOS приходит одно событие на переключение, а не нажатие и отпускание.
- [x] `GameContext.controls: { readonly bindings; subscribe(listener) }` — игра только читает раскладку, меняет её платформа.
- [x] Тесты:
  - загрузка: пустое хранилище → `defaults`; мусор и запрещённые клавиши выброшены; новое действие получает свою клавишу по умолчанию, а если она занята — остаётся пустым;
  - конфликт: `{ conflict }` без изменений, затем `replace: true` переносит клавишу;
  - `reset()` возвращает `defaults` и сохраняет их.

#### 5. Подписи клавиш

- [x] `keyLabel(code, layoutMap?)` в платформе:
  - буквы (`KeyW`): значение из `navigator.keyboard.getLayoutMap()`, **если это латиница**. На AZERTY `KeyQ` даёт «A», и это правильно. На русской раскладке получится «Ц», а на клавише обычно есть и W, и Ц, и в играх принято писать W — поэтому кириллицу заменяем латиницей из `code`;
  - не буквы — таблица: `Space` → «Пробел», `ShiftLeft` → «Левый Shift», `ArrowUp` → «↑», `Digit1` → «1», `Numpad1` → «Num 1» и так далее;
  - неизвестный `code` — сам `code`, а не пустая строка.
- [x] `getLayoutMap()` есть только в Chromium и только в защищённом контексте; он асинхронный. Без него работает таблица и латиница из `code`.
- [x] Тесты: русская раскладка, AZERTY, без раскладки, неизвестный `code`.

#### 6. Состояние игры: `GameContext.play`

Кто сейчас «главный» — меню, игра или пауза — решает **платформа**: она рисует меню. Игра узнаёт об этом и может попросить паузу.

- [x] Состояния платформы: `loading → menu → playing ⇄ paused`, из `paused` можно вернуться в `menu`. Игра видит только `menu | playing | paused`; `loading` значит, что `mount` ещё не закончился.
- [x] Переходы — **чистый редьюсер** без React, с тестами. Недопустимый переход (пауза в меню, «Играть» во время загрузки) молча игнорируется.
- [x] Контракт:

  ```ts
  play: {
    readonly state: "menu" | "playing" | "paused";
    /** Вызывается синхронно, внутри того же клика, что сменил состояние (см. подсказки). */
    subscribe(listener: (next: PlayState, previous: PlayState) => void): () => void;
    /** Игра просит паузу: мышь отпущена, вкладка скрыта. */
    pause(): void;
  }
  ```

  `previous` нужен, чтобы отличить «Продолжить» (`paused → playing`) от новой игры (`menu → playing`).

- [x] `mountGame` получает `onReady()`: вызывается один раз после успешного `mount` и не вызывается, если страницу покинули раньше. Тест рядом с существующими тестами `mountGame`.

#### 7. Захват мыши по команде (`createInput`)

Сейчас мышь захватывается только по клику на canvas. Теперь её захватывает кнопка «Играть» или «Продолжить» в меню платформы.

- [x] `input.lock(): Promise<boolean>` — `false`, если браузер отказал (см. подсказку про задержку после Esc). `input.unlock()` — только свой захват.
- [x] `PointerOptions.onUnlock?: () => void` — захват потерян: Esc, переключение окна, `unlock()`.
- [x] Клик по canvas по-прежнему захватывает мышь: это запасной путь, если `lock()` не сработал.
- [x] Тесты с `FakeDocument`, как в M1-03: `lock()` успешный и отклонённый, `onUnlock` по `pointerlockchange`.

### Часть B · Bridge

#### 8. Реакция на `play`

- [x] **`mount` больше не запускает цикл.** Мир, модель и физика готовы, рисуется **один кадр** — аватар на старте. Это фон главного меню.
- [x] `menu → playing` — новая игра:
  - `input.lock()` прямо в обработчике (подсказки);
  - если до этого уже играли, мир возвращается в начало: `sim.restore(initial)`, где `initial = sim.snapshot()` сразу после `createSim`. Пересоздавать Rapier-мир не нужно;
  - `loop.start()`.
- [x] `paused → playing` — «Продолжить»: `input.lock()` и `loop.start()`. Цикл сам отбросит время паузы: `start()` сбрасывает отсчёт.
- [x] `→ paused` и `→ menu`: `loop.stop()`. Если пауза пришла от платформы, а не от Esc, ещё `input.unlock()`.
- [x] Игра просит паузу (`play.pause()`):
  - по `onUnlock`, если сейчас `playing`;
  - по `document.visibilitychange` → `hidden`: переключил вкладку — пауза, а не бег в провал.

  В одиночной игре пауза останавливает цикл. В M2 матч на сервере идёт дальше: меню только закрывает экран, а ввод перестаёт уходить. Это решение 10, сейчас ничего делать не нужно.

- [x] **Пока цикл стоит, кадр рисуется по требованию:**
  - после изменения размера: `renderer.setSize` очищает canvas, и за меню остаётся чёрный экран;
  - после изменения настроек: FOV меняется в паузе и сразу виден за полупрозрачным меню.

  Например, функция `redraw()` с последним состоянием и `alpha = 1`, и `createView` получает `onResize`.

#### 9. Настройки и клавиши на лету

- [x] FOV: `settings.subscribe` → `camera.fov = verticalFov(fov)`, `camera.updateProjectionMatrix()`. Прицел не съедет: камера стоит на луче прицела (M1-03), и центр экрана от FOV не зависит.
- [x] Клавиши: `DEFAULT_BINDINGS` и подписи действий уезжают в `controls` для `defineGame`. При запуске — `input.setBindings(ctx.controls.bindings)`, затем подписка.
- [x] HUD:
  - убрать «Кликни, чтобы играть» и строку со всеми клавишами: теперь это главное меню и вкладка «Клавиши»;
  - оставить запасной вариант: `playing`, но мышь не захвачена → «Кликни, чтобы продолжить»;
  - подсказки «Недоступно: …» остаются.
- [x] Отписки — в `unmount`, в обратном порядке создания, как сейчас.

- [ ] **Каталог:** кнопка «Настройки» в шапке открывает тот же экран, только с вкладкой «Общие»: игры там нет.

## Критерии приёмки

Вручную в Chrome, затем в Safari и Firefox:

- **Главное меню:**
  - на `/play/bridge` сразу видно меню с «Загрузка…», затем «Играть» становится активной;
  - по «Играть» мышь захватывается сразу, без второго клика.
- **Пауза:**
  - Esc → меню паузы, аватар стоит, тики не идут;
  - «Продолжить» возвращает в игру без рывка;
  - если «Продолжить» нажать в первую секунду после Esc, видна «Кликни, чтобы продолжить», а клик по canvas её снимает;
  - переключение вкладки во время игры → пауза.
- **Новая игра:** «В главное меню» → «Играть» — аватар снова на старте.
- **Настройки:**
  - FOV меняется на лету и в паузе;
  - чувствительность и инверсия мыши действуют сразу после «Продолжить»;
  - после перезагрузки всё сохранено;
  - во второй открытой вкладке громкость и FOV обновились сами.
- **Клавиши:**
  - переназначил прыжок на `F` — прыгает по `F`, а `Space` больше не прыгает;
  - конфликт предлагает замену;
  - «Сбросить» возвращает стандартные;
  - Esc, Ctrl и F5 назначить нельзя.
- **Каталог:** кнопка «Настройки» открывает общие настройки без вкладки «Клавиши».
- **С клавиатуры:** все меню и экраны проходятся Tab, Enter и Esc.
- **Без регрессий:** движение, прыжок, присед, прицел и камера из M1-03 и M1-09; модель из M1-10; уход со страницы во время загрузки.
- `bun run typecheck`, `bun run test`, `bun lint --max-warnings=0`, `bun fmt --check`, CI зелёный.

## Подсказки

- **Захват мыши — только из действия пользователя.** Браузер разрешает `requestPointerLock()` вскоре после клика или нажатия клавиши (transient activation). Поэтому `play.subscribe` вызывает подписчиков **синхронно**, внутри `onClick` кнопки «Играть». Не откладывай смену состояния до `useEffect`: в Chromium окно активации — несколько секунд, и сработает, но в других браузерах это может не пройти.
- **Esc — не действие пользователя.** По спецификации HTML Esc не даёт transient activation. Поэтому продолжить по Esc из меню паузы нельзя, и меню на Esc не реагирует. Заодно не случится, что то же нажатие Esc, которое отпустило мышь, сразу закроет только что открытую паузу.
- **Chrome не даёт снова захватить мышь сразу после Esc:** в течение ~1 с `requestPointerLock` отклоняется («The user has exited the lock before this request was completed»). Отсюда `lock(): Promise<boolean>` и запасная надпись «Кликни, чтобы продолжить». Не маскируй ошибку повторными попытками в цикле.
- **`createInput` игнорирует клавиши, пока мышь не захвачена** (M1-03). Поэтому, пока игрок назначает клавишу на экране настроек, аватар не побежит: отдельно глушить ввод игры не нужно.
- **Захват клавиши на экране настроек:** слушай `keydown` в фазе захвата (`capture: true`), бери `event.code`, вызывай `preventDefault()` и `stopPropagation()`, пропускай `event.repeat`. Иначе Space прокрутит страницу, а Esc закроет экран.
- **`renderer.setSize()` очищает canvas.** Пока цикл стоит, после каждого изменения размера нужно перерисовать кадр, иначе за меню будет чёрный экран.
- **Раскладку хранит платформа, а не игра.** Игра только объявляет `controls` и читает `ctx.controls`. Тогда проверка, сброс и конфликты написаны один раз для всех игр.
- **Хранилище — граница доверия**, как `games:settings` в M0-05: всё, что пришло из `localStorage`, проверяется схемой, а битое заменяется значением по умолчанию.
- **Не тащи React в игру.** Решение 10: каркас меню рисует платформа. Игра знает только `ctx.play`, `ctx.controls`, `ctx.settings` и `ctx.storage`. `mountGame` и код игры остаются без фреймворка (`CLAUDE.md`).
