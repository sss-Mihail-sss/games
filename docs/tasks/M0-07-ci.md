# M0-07 · CI на GitHub Actions

## Цель

Сейчас проверки (`typecheck`, тесты, линтер, сборка) запускаются только руками. За M0 это уже стоило:

- коммит из #5 потерялся: PR влили за минуту до пуша, и никто этого не заметил;
- три PR влиты до ревью без единой автоматической проверки;
- GitHub показывает зелёную кнопку слияния, даже если `main` за это время ушёл вперёд и комбинация не собирается. Перед слиянием #8–#10 это пришлось проверять руками.

В M1 придут физика на WASM и больше кода, поэтому ручные проверки станут дороже и будут забываться чаще.

**Результат задачи:**

1. Один workflow на каждом PR и пуше в `main`. Он повторяет наш Definition of Done и проверяет production-сборку под Bun так, как она будет работать в Docker.
2. Правило: в `main` попадает только PR с зелёным CI. Или осознанное и записанное решение, почему пока без этого правила (см. шаг 5).

**Порядок:** шаг 1 → шаг 2 (пуш, первый прогон) → шаг 3 → шаг 4 → шаг 5 → шаг 6. После шага 2 CI уже работает, дальше он только растёт.

## Что сделать

### 1. Версии в одном месте

**Зачем.** CI должен запускать ту же версию Bun, что у тебя локально. Иначе «у меня работает» и «в CI падает» будут расходиться из-за версии Bun, а не из-за кода. Обновление Bun тогда становится обычным PR с видимым диффом.

- [x] В корневой `package.json` добавь `"packageManager": "bun@1.4.5"`. `oven-sh/setup-bun` с `bun-version-file: package.json` читает именно это поле: берёт часть после `bun@`, а если поля нет — `engines.bun`.
- [x] `@types/bun` в корневом `package.json` сейчас стоит `latest`. Это единственная зависимость, которая обновляется сама при любом `bun install` с удалённым lock-файлом. Переведи её в `catalog:` с точной версией. Установленную версию покажет `bun pm ls | grep @types/bun`, сейчас это 1.4.4.
- [x] `bun install`, затем `git diff bun.lock`: в lock-файле должна поменяться только строка `@types/bun`.

**Проверь себя.** `bun run typecheck`, `bun run test`, `bun lint`, `bun fmt --check` проходят так же, как до изменений.

### 2. Workflow: `.github/workflows/ci.yml`

**Зачем.** Это сердце задачи: тот же Definition of Done, но автоматически и на каждом PR.

**Каркас файла** (порядок секций):

```
name: CI
on: …              # pull_request + push в main
concurrency: …     # один прогон на ветку
permissions: …     # только чтение
jobs:
  ci:
    runs-on: ubuntu-latest
    timeout-minutes: …
    env: …
    steps: …
```

- [ ] **Триггеры:** `pull_request` (на любую ветку) и `push` с `branches: [main]`. Пуш в `main` нужен, чтобы видеть, что `main` после слияния зелёный. Именно здесь ловится случай, когда два зелёных PR вместе ломают сборку.
- [ ] **`concurrency`:** группа по ветке, например `ci-${{ github.ref }}`, и `cancel-in-progress: true`. Пушишь в PR три раза подряд — работает только последний прогон.
- [ ] **`permissions: contents: read`.** Workflow ничего не пишет в репозиторий. По умолчанию у токена Actions прав больше, их стоит урезать явно.
- [ ] **`timeout-minutes: 10`.** Если, например, smoke-сервер не поднимется, job не будет висеть 6 часов по умолчанию.
- [ ] **`env: NEXT_TELEMETRY_DISABLED: 1`:** Next в CI не должен ничего никуда отправлять.
- [ ] **Шаги**, каждый с понятным `name`, чтобы в логе сразу было видно, что упало:
  1. `actions/checkout@v7`.
  2. `oven-sh/setup-bun@v2` с `bun-version-file: package.json`.
  3. `bun install --frozen-lockfile`. Если `bun.lock` не совпадает с `package.json`, шаг падает. Так ловится «поменял зависимость и забыл закоммитить lock», и не только это: недавно у тебя в рабочей копии сам собой сдвинулся `bun.lock`.
  4. `bun run typecheck`. Он сам запускает `next typegen`, без этого типы `next/root-params` в CI были бы `any`.
  5. `bun run test`.
  6. `bun lint --max-warnings=0`. Сейчас «No problems» мы проверяем глазами, а предупреждение не роняет exit code. С этим флагом роняет. Флаг проходит через корневой скрипт `lint` (проверено).
  7. `bun fmt --check`.
  8. `bun run --filter web build`.
- [ ] **Имя job — `ci`.** Ровно так будет называться обязательная проверка в шаге 5.
- [ ] Закоммить, запушь ветку и открой черновик PR. Убедись, что на PR появилась проверка `ci` и она зелёная. До шага 3 этого достаточно.

**Проверь себя.**

- Открой лог прогона и найди строку с версией Bun: должна быть 1.4.5.
- Посмотри, сколько занял каждый шаг. Цифры понадобятся в шаге 6.

### 3. Smoke-проверка production-сборки: `scripts/smoke.ts`

**Зачем.** Это обещание из ARCHITECTURE.md (раздел «Web: Next.js», риск «Next тестируется на Node»). Сборка может пройти, а сервер под Bun — упасть при старте или отдать 500. Тогда это должно падать в CI, а не на проде. И проверяем мы именно то, что пойдёт в Docker: standalone-сервер, а не `next start`.

Логику держим в TypeScript-скрипте, а не в bash внутри YAML: его можно запустить локально, он типизирован и читается.

- [ ] **Подготовка сборки (шаг workflow перед скриптом).** Standalone-сборка не копирует статику сама. Рядом с `apps/web/.next/standalone/apps/web/server.js` нужно положить:
  - `apps/web/public` → `…/standalone/apps/web/public`;
  - `apps/web/.next/static` → `…/standalone/apps/web/.next/static`.

  Это можно сделать прямо в скрипте (`Bun.$\`cp -R …\``) — тогда локальный запуск тоже готовит всё сам.

- [ ] **Запуск сервера:** `Bun.spawn(["bun", "server.js"], { cwd, env: { ...process.env, PORT, HOSTNAME: "127.0.0.1" } })`. Порт возьми не 3000, чтобы скрипт не конфликтовал с запущенным `bun run dev`, например 4173. Можно разрешить переопределить его через `SMOKE_PORT`.
- [ ] **Ожидание готовности:** опрашивай `fetch` на `/ru` каждые 200 мс, пока не придёт ответ, с общим таймаутом, например 15 с. Не `sleep 5`: это и медленно, и ненадёжно.
- [ ] **Проверки** — таблица ожиданий, а не россыпь `if`:

  | Запрос            | Ожидание                                         |
  | ----------------- | ------------------------------------------------ |
  | `/`               | 307, заголовок `location` заканчивается на `/ru` |
  | `/ru`             | 200, в HTML есть `<html lang="ru">`              |
  | `/ru/play/bridge` | 200, в HTML есть `og:title`                      |
  | `/ru/play/nope`   | 404                                              |
  | `/robots.txt`     | 200, есть строка `Sitemap:`                      |
  | `/sitemap.xml`    | 200                                              |

  Для редиректа нужен `fetch(url, { redirect: "manual" })`, иначе `fetch` сам пройдёт по редиректу и вернёт 200.

- [ ] **Вывод:** по строке на проверку (✓/✗, путь, что ожидали и что получили). При любом ✗ — `process.exit(1)`.
- [ ] **Остановка сервера в `finally`** (`proc.kill()`), даже если проверка упала или вышел таймаут. Иначе локально останется висящий процесс на порту.
- [ ] **Типы и линтер для скрипта.** Корневой `tsconfig.json` проверяет только проекты из `references`. Добавь `scripts/tsconfig.json` (расширяет `tsconfig.base.json`, `include: ["."]`) и ссылку на него в корневые `references`, иначе `bun run typecheck` скрипт пропустит.
- [ ] **Шаг в workflow** после сборки: `bun scripts/smoke.ts`.

**Проверь себя (локально).**

1. `bun run --filter web build && bun scripts/smoke.ts` — всё ✓, код выхода 0 (`echo $?`).
2. Поменяй в таблице ожиданий 404 на 200 — скрипт пишет ✗ с понятным сообщением и выходит с 1. Верни.
3. Временно поставь таймаут ожидания 1 мс — скрипт падает по таймауту, и после него не остаётся процесса на порту: `lsof -i :4173` ничего не выводит.

### 4. Убедиться, что CI действительно ловит ошибки

**Зачем.** CI, который ни разу не был красным, ничего не доказывает. Он может быть зелёным просто потому, что ничего не проверяет: шаг не запустился, флаг не передался, команда упала, но вернула 0.

Чтобы не пачкать историю `m0-07-ci` откатами, сделай это в одноразовой ветке:

- [ ] `git switch -c m0-07-ci-red`, черновик PR в `main`.
- [ ] Три отдельных коммита, после каждого пуш и ожидание прогона:
  1. сломанный тест (`expect(1).toBe(2)` в любом тесте) → красный шаг `test`;
  2. сломанное форматирование (лишние пробелы в любом `.ts`) → красный шаг `fmt --check`;
  3. версия зависимости в `package.json` поменяна без `bun install` → красный шаг `install --frozen-lockfile`.

  Каждый следующий коммит сначала чинит предыдущую поломку, иначе всё будет падать на первом сломанном шаге.

- [ ] Ссылки на три красных прогона положи в описание PR `m0-07-ci`. Потом закрой PR `m0-07-ci-red` и удали ветку.

### 5. Правило для `main`

**Зачем.** Без правила CI только сигнализирует: красный PR всё равно можно влить. С правилом кнопка слияния неактивна, пока проверка `ci` не зелёная.

- [ ] Settings → Rules → Rulesets → New branch ruleset, цель — ветка по умолчанию (`main`):
  - **Require a pull request before merging** — никаких прямых пушей в `main`;
  - **Require status checks to pass** → добавь `ci`. Проверка появится в списке, только когда job уже хотя бы раз отработал (шаг 2);
  - **Require branches to be up to date before merging** — главное против случая «два зелёных PR вместе ломают `main`»: GitHub заставит обновить ветку и прогнать CI заново;
  - **Block force pushes** и **Restrict deletions**.
- [ ] **Учти: у нас приватный репозиторий на личном аккаунте.** На бесплатном плане GitHub правила для приватных репозиториев не применяются. Если в настройках увидишь, что правило не действует, вариантов три:
  - GitHub Pro;
  - сделать репозиторий публичным;
  - оставить CI сигналом без блокировки: ✅/❌ на PR видны, но кнопка слияния остаётся активной.
- [ ] Запиши выбор в описание PR и в `docs/tasks/README.md` (раздел «Как работаем»): от него зависит, насколько можно полагаться на «красный CI = не вливаем».

### 6. Скорость и документы

- [ ] **Время прогона меньше 4 минут.** Если дольше, найди по логу медленный шаг:
  - `bun install` медленный → кеш `~/.bun/install/cache` через `actions/cache` с ключом `bun-${{ runner.os }}-${{ hashFiles('bun.lock') }}`;
  - сборка Next медленная → пока ничего не делаем, у нас она занимает секунды.

  Начни без кеша и добавляй его, только если замер это оправдывает. Каждый кеш — ещё одна вещь, которая может «залипнуть».

- [ ] В `docs/tasks/README.md` в Definition of Done пункт «CI на PR зелёный (после M0-07)» теперь действует: убери «(после M0-07)».
- [ ] В ARCHITECTURE.md в строке про smoke-проверку замени «В CI будет smoke-проверка…» на ссылку на workflow и `scripts/smoke.ts`.

## Критерии приёмки

- На PR `m0-07-ci` есть проверка `ci`, она зелёная, в логе Bun 1.4.5.
- В описании PR есть три ссылки на красные прогоны (тест, форматирование, lock-файл), каждый упал на своём шаге.
- `bun scripts/smoke.ts` после локальной сборки проходит. Если сломать ожидание или таймаут, он падает с кодом 1 и не оставляет процесс на порту.
- Скрипт проверяется `typecheck` (`scripts/tsconfig.json` в `references`) и линтером.
- Прогон занимает меньше 4 минут; время каждого шага записано в описании PR.
- Правило для `main` включено, или в README записано, почему нет и что вместо него.
- `bun run typecheck`, `bun run test`, `bun lint --max-warnings=0`, `bun fmt --check` проходят локально.

## Подсказки

- **Не `next start`.** Мы деплоим standalone-сервер, и проверять надо его. `next start` при `output: "standalone"` к тому же печатает предупреждение.
- **`HOSTNAME`.** Standalone-сервер Next слушает адрес из переменной окружения `HOSTNAME`. В Docker она по умолчанию равна id контейнера, в shell часто — имени машины, и тогда сервер слушает не тот адрес. Поэтому всегда задавай её явно: `HOSTNAME=127.0.0.1` в smoke-скрипте и `HOSTNAME=0.0.0.0` в будущем Dockerfile.
- **Отладка YAML.** Если workflow не запускается вовсе, смотри вкладку Actions: ошибки синтаксиса YAML видны там, а не в PR.
- **Секретов не нужно,** workflow работает только на чтение. Если появится желание добавить токен — это повод остановиться и обсудить.
- **Версии actions** — `checkout@v7` и `setup-bun@v2` — проверены на дату тикета. Мажорная версия в теге (`@v7`) получает исправления сама, а при смене мажорной версии обновляем вручную.
