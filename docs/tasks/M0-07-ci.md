# M0-07 · CI на GitHub Actions

## Цель

Сейчас проверки (`typecheck`, тесты, линтер, сборка) запускаются только руками. За M0 это уже стоило:

- коммит из #5 потерялся: PR влили за минуту до пуша, и никто этого не увидел;
- три PR влиты до ревью, без единой автоматической проверки.

В M1 придут физика на WASM и больше кода, поэтому ручные проверки станут дороже и будут забываться чаще.

Задача — один workflow, который на каждом PR и пуше в `main` повторяет наш Definition of Done и обещанную в ARCHITECTURE.md smoke-проверку Next под Bun. Плюс правило: в `main` попадает только зелёный PR.

## Что сделать

### 1. Версия Bun в одном месте

- [ ] В корневом `package.json`: `"packageManager": "bun@1.4.5"`. Локально и в CI будет одна и та же версия, а обновление Bun станет обычным PR с видимым диффом.
- [ ] `@types/bun` в корневом `package.json` сейчас стоит `latest`. Переведи его в `catalog:` с точной версией, иначе типы Bun будут обновляться сами по себе.

### 2. Workflow `.github/workflows/ci.yml`

- [ ] Триггеры: `pull_request` и `push` в `main`.
- [ ] `concurrency`: новый пуш в тот же PR отменяет старый прогон (`cancel-in-progress: true`).
- [ ] `permissions: contents: read` — workflow ничего не пишет в репозиторий.
- [ ] Шаги, по порядку:
  1. `actions/checkout@v7`.
  2. `oven-sh/setup-bun@v2` с `bun-version-file: package.json`.
  3. `bun install --frozen-lockfile`. Если `bun.lock` не совпадает с `package.json`, CI падает — так ловится «забыл закоммитить lock».
  4. `bun run typecheck`. Он сам запускает `next typegen`, без этого типы `next/root-params` неполные.
  5. `bun run test`.
  6. Линтер так, чтобы предупреждения тоже роняли CI. Сейчас «No problems» мы проверяем глазами. Смотри `bun lint --help`: флаг `--max-warnings`. Учти, что корневой скрипт `lint` вызывает `bun lint` (см. `--no-script`).
  7. `bun fmt --check`.
  8. `bun run --filter web build`.
- [ ] Имя job — например, `ci`. Это имя будет обязательной проверкой в шаге 4.

### 3. Smoke-проверка production-сборки под Bun

Это обещание из ARCHITECTURE.md (раздел «Web: Next.js», риск «Next тестируется на Node»). Если обновление Next сломает работу под Bun, это должно упасть в CI, а не в проде.

- [ ] После сборки запусти standalone-сервер так, как он будет работать в Docker:
  - скопируй `public` и `.next/static` рядом с `.next/standalone/apps/web/server.js`;
  - запусти `bun .next/standalone/apps/web/server.js` в фоне на свободном порту.
- [ ] Дождись готовности: опрашивай порт с таймаутом, а не `sleep 5`.
- [ ] Проверь `curl`-ом:
  - `/` → 307 на `/ru`;
  - `/ru` → 200, в HTML есть `<html lang="ru">`;
  - `/ru/play/bridge` → 200, в HTML есть `og:title`;
  - `/ru/play/nope` → 404;
  - `/robots.txt` и `/sitemap.xml` → 200.
- [ ] Вынеси проверку в скрипт, например `scripts/smoke.ts` на `Bun.$` и `fetch`, чтобы его можно было запустить и локально. Длинный bash прямо в YAML плохо читается и не тестируется.

### 4. Правило для `main`

- [ ] Settings → Rules → Rulesets (или Branches → Branch protection) для `main`:
  - слияние только через PR;
  - обязательная проверка `ci`;
  - запрет force-push и удаления ветки.
- [ ] **Учти:** у нас приватный репозиторий на личном аккаунте. На бесплатном плане GitHub правила для приватных репозиториев не применяются. Если в настройках увидишь, что правило не действует, есть три варианта:
  - GitHub Pro;
  - сделать репозиторий публичным;
  - оставить CI как сигнал без блокировки: на PR будет видно ✅/❌, но кнопка слияния останется активной.

  Выбери и напиши, что выбрал: от этого зависит, насколько можно полагаться на «красный CI = не вливаем».

### 5. Документы

- [ ] В `docs/tasks/README.md` в Definition of Done добавь «CI на PR зелёный».
- [ ] В ARCHITECTURE.md в строке про smoke-проверку замени «будет» на ссылку на workflow.

## Критерии приёмки

- На этом PR в GitHub видна проверка `ci`, и она зелёная.
- **Проверка, что CI действительно ловит ошибки.** В отдельном временном коммите сломай по очереди:
  - тест;
  - форматирование;
  - lock-файл (поменяй версию в `package.json` без `bun install`).

  Каждый раз CI должен стать красным на нужном шаге. Потом откати эти коммиты, а ссылки на красные прогоны приложи к PR.

- Smoke-скрипт запускается локально (`bun scripts/smoke.ts` после сборки) и падает, если, например, остановить сервер или поменять ожидаемый статус.
- Прогон занимает меньше 4 минут. Если дольше, посмотри, что медленное: обычно это кеш `bun install` или сборка Next.
- Правило для `main` включено, или в PR записано, почему нет (см. шаг 4).

## Подсказки

- **Кеш.** `setup-bun` кеширует сам бинарник Bun. Для зависимостей можно добавить `actions/cache` на `~/.bun/install/cache` с ключом от `hashFiles('bun.lock')`. Начни без кеша, замерь время, и добавляй кеш только если `bun install` заметно тормозит.
- **Turbopack кеширует сборку в `.next/cache`.** Кешировать его в CI пока не нужно: сборка у нас идёт секунды.
- **Не запускай `next start`.** Мы деплоим standalone-сервер, и проверять надо именно его. `next start` при `output: "standalone"` к тому же печатает предупреждение.
- **Порт для smoke** выбери не 3000, чтобы локальный запуск скрипта не конфликтовал с `bun run dev`.
- **Секретов не нужно,** workflow работает только на чтение. Если появится желание добавить токен — это повод остановиться и обсудить.
