# M0-06 · Заглушка bridge

## Цель

Первая настоящая игра в каталоге: 3D-сцена, по которой аватар ходит на WASD, а камеру можно вращать мышью. Задача проверяет всю цепочку M0 на живой игре:

- контракт `defineGame`;
- фиксированный цикл и интерполяцию;
- ввод, включая новое поле `yaw` в `InputFrame`;
- оболочку `web` и полную очистку ресурсов.

Физики пока нет, она появится в M1.

Главное в задаче — не картинка, а граница `sim` / `client`. `sim` — это чистая функция «состояние + ввод → новое состояние». В M2 тот же код будет крутиться на сервере, а клиент будет предсказывать по нему свой аватар. Всё, что попадёт в `sim` из DOM или Three.js, сервер не соберёт.

## Что сделать

### 0. Зависимости

- [x] `three` и `@types/three` версии `0.187.0` — в `catalog` корневого `package.json`, в `games/bridge` подключить через `catalog:`.
- [x] Three.js подключается только в `games/bridge/src/client/`. Каталог `web` его не видит: пакет игры загружается лениво (M0-05). После сборки проверь, что `three` попал в чанк игры, а не в JS каталога.

### 1. `InputFrame` v2: поле `yaw` (`@repo/game-protocol`)

Сейчас W — это «вперёд по оси −Z мира». Когда камера повернётся, игрок будет ждать «вперёд от камеры». Камеры в `sim` нет, поэтому её поворот приходит как часть ввода. Тогда сервер в M2 получит его так же, как нажатые клавиши.

- [x] `InputFrame` получает поле `yaw: number` — поворот камеры вокруг оси Y, **квантованный в uint16**: `0…65535` соответствуют `[0, 2π)`.
- [x] Хелперы `quantizeYaw(radians): number` и `yawToRadians(units): number`. Любой угол, включая отрицательный и больше 2π, заворачивается в диапазон: `quantizeYaw(-π/2)` равно `quantizeYaw(3π/2)`, `quantizeYaw(2π)` равно `0`.
- [x] Кодек: `VERSION = 2`, размер 19 байт (1 + 4 × uint32 + uint16). Кадр версии 1 отклоняется с `InputFrameDecodeError`, как и любая чужая версия. Совместимость не нужна: развёрнутых клиентов ещё нет.
- [x] Тесты:
  - кодек: round-trip с `yaw`;
  - кодек: v1 и неверный размер отклоняются;
  - `quantizeYaw`: заворачивание углов;
  - `yawToRadians(quantizeYaw(a))` отличается от `a` не больше чем на шаг квантования `2π / 65536`.

### 4. `sim/` — симуляция

Состав папки: `index.ts`, `type.ts`, `actions.ts`, `sim.ts`, `sim.test.ts`, `boundary.test.ts`, `tsconfig.json`.

- [x] `actions.ts`: `defineActions(["forward", "back", "left", "right"] as const)`. Список общий для клиента и будущего сервера.
- [x] `type.ts`: состояние мира `SimState` с одним аватаром — позиция `x`, `z` в метрах и `facing` (куда смотрит аватар, радианы). Высоты нет: без физики аватар всегда стоит на `y = 0`.
- [x] `sim.ts`:
  - `TICK_RATE = 30`, скорость ходьбы `WALK_SPEED` (около 4 м/с), границы мира;
  - `createInitialState()`: аватар на левом берегу лицом к провалу;
  - `step(state, frame: InputFrame, dt): SimState` — **чистая функция**: не меняет `state`, возвращает новый объект, не читает время, не использует `Math.random`.
- [x] Движение:
  - направление из клавиш, повёрнутое на `yawToRadians(frame.yaw)`;
  - диагональ нормализуется;
  - позиция ограничена границами мира;
  - `facing` поворачивается в сторону движения, а при нулевом вводе остаётся прежним.
- [x] Провал аватар пока проходит насквозь, как по невидимому мосту. Это нормально: падение — работа физики в M1.
- [x] Тесты `step`:
  - нулевой ввод не меняет позицию и `facing`;
  - `forward` при `yaw = 0` двигает по −Z ровно на `WALK_SPEED * dt`;
  - диагональ (`forward` + `right`) за тик проходит то же расстояние, что прямая, а не в √2 раз больше;
  - `forward` + `back` взаимно гасятся;
  - `yaw = π/2`: `forward` двигает по −X (камера повернулась влево, «вперёд» повернулся вместе с ней);
  - граница мира: долгое движение в стену останавливается на границе;
  - чистота: `step` не меняет переданный `state` (проверь `Object.freeze` на входе);
  - детерминизм: одна и та же последовательность кадров даёт одно и то же итоговое состояние.

### 5. `client/` — рендер

Состав папки по смыслу, например: `index.ts` (`defineGame`, сборка всего вместе), `renderer.ts`, `scene.ts`, `camera.ts`.

- [x] **Рендерер** (`renderer.ts`): `WebGLRenderer` на собственном `<canvas>` внутри `element`.
  - Размер следует за контейнером через `ResizeObserver`, а не `window.resize`: игра не знает, какую часть страницы ей дали.
  - `setSize(width, height, false)` — третий аргумент не даёт Three перезаписать CSS-размер canvas.
  - При каждом ресайзе обновляются `camera.aspect` и `updateProjectionMatrix()`. Размер 0 × 0 (скрытый контейнер) пропускай.
  - `pixelRatio = min(devicePixelRatio, cap)`, где `cap` берётся из `ctx.settings.current.quality`: `low` → 1, `medium` → 1,5, `high` → 2.
  - Подпишись на `ctx.settings.subscribe` и меняй `pixelRatio` на лету; в unmount отпишись.
- [x] **Сцена** (`scene.ts`), временные примитивы, масштаб в метрах:
  - два берега (`BoxGeometry`) и провал между ними метров 8–10;
  - внизу «вода» или земля, чтобы провал читался глубиной;
  - `HemisphereLight` + `DirectionalLight`, без теней (тени — в M1);
  - аватар — `CapsuleGeometry` общей высотой около 1,7 м, плюс маленький «нос» (конус или куб), чтобы было видно, куда он смотрит.
  - `createScene()` возвращает объекты и функцию `dispose`, которая освобождает все свои геометрии и материалы.
- [x] **Камера** (`camera.ts`): `PerspectiveCamera` над аватаром и позади него, смотрит на уровень головы.
  - `yaw` меняется перетаскиванием мышью по canvas: `pointerdown` → `setPointerCapture`, `pointermove` → `yaw -= movementX * sensitivity`. Листенеры снимаются через `AbortController`.
  - Камера двигается каждый кадр, а не каждый тик, поэтому вращение плавное на любом мониторе.
  - В `update` на каждом тике в `sample` уходит `quantizeYaw(camera.yaw)`.
  - `OrbitControls` из `three/examples` не подходит: они вращают камеру сами, а нам нужно, чтобы `yaw` был частью ввода и попадал в `InputFrame`.
- [x] **Цикл и интерполяция** (`index.ts`):
  - храни `previous` и `current` состояния `sim`;
  - в `update(tick, dt)`: `previous = current; current = step(current, input.sample(tick, yaw), dt)`;
  - в `render(alpha)`: позиция аватара — `lerp(previous, current, alpha)`, `facing` — интерполяция угла по кратчайшей дуге;
  - камера следует за интерполированной позицией, затем `renderer.render(scene, camera)`.
- [x] Привязки клавиш по умолчанию: WASD плюс стрелки (`"Key:KeyW"`, `"Key:ArrowUp"` и т. д.).
- [x] **Unmount** освобождает всё в обратном порядке создания:
  1. цикл — `loop.stop()`;
  2. ввод — `input.dispose()`;
  3. листенеры камеры — `abort()`;
  4. `ResizeObserver` — `disconnect()`;
  5. подписка на настройки;
  6. геометрии и материалы сцены;
  7. `renderer.dispose()` и `renderer.forceContextLoss()`;
  8. `canvas.remove()`.
- [x] Если `signal` уже отменён, когда `mount` закончил подготовку, сразу вызови unmount. `defineGame` делает unmount идемпотентным, поэтому повторный вызов из `mountGame` безопасен.
- [x] Заглушка из M0-05 (синий canvas) удаляется.

### 6. Необязательно: `Clock` — свойства вместо методов

`Clock` в `game-core/loop/type.ts` объявлен методами (`now(): number`). По нашему соглашению колбэки и зависимости объявляем свойствами (`now: () => number`), иначе правило `unbound-method` ругается при передаче `clock.now` дальше. Если будешь трогать цикл — поправь заодно, тесты цикла не должны поменяться.

## Критерии приёмки

- **Интерполяция.** При 30 Гц движение на мониторе 120–144 Гц плавное, без ступенек. Временно выстави `TICK_RATE = 5`: аватар должен двигаться плавно, но с заметной задержкой реакции на клавиши. Потом верни 30.
- **Камера.** После поворота камеры на 90° клавиша W ведёт аватар «от камеры», а не по старой оси мира. Вращение мышью плавное независимо от частоты тика.
- **Граница `sim`.** Обе пробы из шага 3 (`document` и `import "three"`) роняют проверки. В итоговом коде `sim/` нет импортов из `three`, `client/` и `@repo/game-core`.
- **Очистка** (критерии M0-05 на настоящей игре):
  - в dev (StrictMode) на странице игры один `<canvas>`;
  - 20 переходов «каталог → игра → каталог» без предупреждения «Too many active WebGL contexts»;
  - после ухода со страницы игры `getEventListeners(window)` в консоли DevTools не содержит `keydown`/`keyup` и `blur` от игры;
  - в dev после `dispose` сцены и перед `renderer.dispose()` выведи `renderer.info.memory`: `geometries` должно стать 0 (у заглушки 4 → 0). `textures` остаётся 1: это служебная `DFG_LUT` (16×16) самого Three для PBR-материалов, её освобождает `renderer.dispose()`. Значит, проверяем только геометрии, а текстуры, когда появятся свои (M1), сверяем с этой единицей.
- **Ресайз.** Окно, панель DevTools и масштаб браузера: картинка не растягивается и не мылится.
- **Настройки.** Смена `quality` на `low` в `localStorage` (`games:settings`) и перезагрузка заметно снижают чёткость (`pixelRatio` 1).
- **Размер.** В описании PR — вес чанка игры в КБ gzip. JS каталога не изменился (около 140 КБ).
- `bun run typecheck`, `bun run test`, `bun lint`, `bun fmt --check` проходят.

## Подсказки

- **Порядок:** протокол (1) → ввод (2) → граница и `sim` с тестами (3, 4) → клиент (5). `sim` полностью проверяется тестами ещё до того, как появится первый пиксель.
- **Система координат Three.js:** Y вверх, камера без поворота смотрит в −Z, положительный поворот вокруг Y — против часовой стрелки, если смотреть сверху. Договорись, что `yaw = 0` — это камера без поворота, и проверь это тестами из шага 4.

  <details>
  <summary>Формула направления (если застрянешь)</summary>

  Для камеры с поворотом `θ` вокруг Y:
  - «вперёд» = `(−sin θ, 0, −cos θ)`;
  - «вправо» = `(cos θ, 0, −sin θ)`.

  Направление движения: `forward × (W − S) + right × (D − A)`, затем нормализация, если длина больше нуля.

  </details>

- **Квантуй `yaw` до `sim`, а не только при отправке.** Если клиент предсказывает аватар по точному углу, а сервер считает по квантованному, предсказание будет расходиться с сервером на каждом тике. Поэтому `step` всегда видит `yawToRadians(frame.yaw)`, а не float камеры.
- **Угол по кратчайшей дуге:** при переходе `facing` с 350° на 10° интерполяция без нормализации разности в `[−π, π]` прокрутит аватар на 340° в обратную сторону.
- **Не создавай объекты в `render`:** `new Vector3()` 144 раза в секунду — это мусор для GC и микрофризы. Создай временные векторы один раз при mount и переиспользуй их.
- **`sim` не обязан быть детерминированным между движками:** `Math.sin` в Bun и в Chrome может отличаться в последних битах. Нам это не мешает, потому что сервер авторитарный и поправит клиента. Детерминизм нужен только в пределах одного движка — его проверяют тесты.
- **WebGPURenderer пока не трогаем:** в M0 хватит `WebGLRenderer`. Переход обсудим в M1, когда будет понятна нагрузка.
- **Арт временный.** Сразу делай масштаб в метрах, потом физика скажет спасибо.
